# Web／低記憶體電腦優化紀錄

本輪以低配預設、可追溯的遊戲資產副本及室內按需載入，降低啟動與遊玩成本。目標是約 720p／30 FPS，**目標不是已達成的實測保證**。原始世界、建築輪廓、路線、碰撞、互動與可編輯美術來源保留；沒有更換 Compatibility renderer、開啟 Web 多執行緒或新增部署服務。

**已完成下述本機修改與 Web 驗證，但尚未達成全程穩定 30 FPS。** 最終 `packs-7bd866e6416621ee` 已完成冷／快取啟動比較、18.58 分鐘實際鍵鼠 Web 路線（81 個樣本、零錯誤），以及同版設定、室內與隱藏分頁下載驗證。全景與區域停留接近 30 FPS，但近景行走只有約 8 FPS、跨橋約 12 FPS。移動診斷支持動畫變形／渲染同步仍是後續優化方向。Windows 已匯出，但圖形裝置初始化失敗；4 GB 實機尚未量測。

## 實作與取捨

### 低配與一般畫質

新增可保存的「低配／一般」選項，並保留個別 MSAA 及 30／60／90 FPS 上限。選擇預設組合後，仍可單獨調整兩者。舊版只有 MSAA／FPS 的設定檔會先以低配預設開啟；使用者修改設定時才保存新格式。

| 項目 | 低配預設 | 一般預設 |
| --- | --- | --- |
| 3D 內部解析度 | 等比例限制在 1280×720 內，不放大較小畫面 | 視窗原始解析度 |
| UI／文字 | 保留原始解析度 | 保留原始解析度 |
| 抗鋸齒 | MSAA 關閉 | MSAA 2× |
| FPS 上限 | 30 | 60 |
| 細節預載／啟用／卸載距離 | 33／27／45 m | 45／38／57 m |
| 卸載延遲 | 4 秒 | 4 秒 |
| 非碰撞蕨類、香蒲、睡蓮密度 | 固定分散保留約 60% | 100% |
| 湖面／海上動物與交通更新 | 每 0.1 秒 | 每幀 |
| 全景縮近時 | 維持簡化總覽 | 允許附近完整細節 |

3D 採用 Compatibility 確實支援的 bilinear 內部縮放，UI 與物理更新率不變；可由 [Godot 4.7 GLES3 render buffer 實作](https://raw.githubusercontent.com/godotengine/godot/4.7-stable/drivers/gles3/storage/render_scene_buffers_gles3.cpp)核對。沒有使用 TAA／FXAA，也沒有變更引擎渲染器。1280×800 視窗的等比例目標是 1152×720，不能寫成每種螢幕都固定 1280×720。

畫質代價是 3D 邊緣較柔、低配關閉 MSAA 後可見鋸齒、遠景植被較少，非必要動物與交通移動更新較疏。角色控制、相機、物理及碰撞不因 10 Hz 動物更新而降頻。最終 Web 的實際 GL viewport 尺寸與畫面驗證列於後續測試表。

最終尺寸依邏輯畫布與 stretch transform 計算一次；避免 `canvas_items` 模式將 UI 縮放重複計入，造成設定顯示「低配」卻未降低真正 3D 尺寸。Web 檢查直接觀察 GL viewport：1200×800 視窗保留原有比例留邊後，UI 為 1200×750，低配 3D 為 1152×720；切一般畫質回到 1200×750。設定保存、恢復預設、調整視窗後均重新檢查，不只看計算出的遙測值。

### 全景：減少葉片與材質批次

原場景已有 LOD、按區域／材質合併與 MultiMesh。本輪新增的是離線遠景葉片取樣，以及適用的不透明常數 albedo 烘焙進頂點色後再合併材質；沒有把既有 MultiMesh 重新算成成果。

| 資產／固定鏡頭指標 | 修改前 | 修改後 |
| --- | ---: | ---: |
| 分區總覽三角形 | 1,009,913 | 755,561（−25.19%） |
| 分區總覽頂點 | 893,393 | 594,843（−33.42%） |
| 三個永久場景檔大小 | 23,507,853 B | 18,469,238 B |
| 分區總覽 MeshInstance | 150 | 61 |
| 靜態比較 draw calls | 217 | 128 |
| 永久碰撞 body／細節 chunks | 384／86 | 384／86 |

固定鏡頭數據來自相同 MX330、1200×750、無 MSAA、3D scale 1.0 的原生靜態場景，不包含角色／HUD／完整世界串流；不是 Web FPS。保護的地面、道路與岸線本身就有 392,688 個三角形，因此本輪沒有硬湊 20～30 萬的試驗預算。較激進的 10% LOD 曾造成屋頂／面板輪廓流失，已撤回，最終仍採 20% 下限。三個實際角度已比對，生成器同步修改。

完整選擇理由、測試與圖片索引：[低配全景紀錄](low-overview-optimization.md)。

### 小地圖：移除持續的 CPU 重算

持續卡頓也有 2D 腳本原因。原小地圖每 0.05 秒重新建立繪圖命令，即使人物完全靜止，仍重算球面投影、裁切與多邊形三角化；這已用實際 CanvasItem `_draw` 通知的 CPU 探針確認。

改為保留未變的畫布繪圖命令，只有人物球面位置、地圖尺寸／範圍或地圖資料改變時重畫。朝向箭頭獨立在小型 overlay 更新，轉身不必重算整張地圖。同一次重畫裡共用海岸／水面的投影結果，之後即清空，快取不會隨走訪地點持續增長。低配地圖更新上限為 10 Hz，一般 20 Hz；主相機、角色控制與物理不降頻。

以下採用重新連續執行的 [HEAD 基準](../deliverables/low-end/minimap-paired-before.json)與[修改後](../deliverables/low-end/minimap-paired-after.json)配對，使用相同探針、相同路線，各位置約 0.8 秒；兩檔記錄各自來源 SHA-256。較早不同背景負載的診斷數字不混入比較。

| 小地圖 CPU 樣本 | 原重畫次數／單次平均 | 新重畫次數／單次平均 |
| --- | ---: | ---: |
| 興趣輔導室靜止 | 14／4.046 ms | 0／無重畫 |
| 橋面靜止 | 14／7.208 ms | 0／無重畫 |
| 練功區靜止 | 13／3.027 ms | 0／無重畫 |
| 同路線移動 | 14／3.710 ms | 14／2.523 ms |

這只有一組短時間原生 headless CPU 配對，沒有完整 3D 世界／GPU，分項計時也有開銷。新導航 overlay 的額外繪製未獨立量測，上表是地圖本體重畫成本；不是 Web FPS，不能據此保證固定的整體效能倍率。最終 Web 路線另外量實際產品差異。

### 角色：減少逐幀布料形態資料

建立 `game/assets/character/runtime/` 副本，沒有減少角色面數，也沒有刪除來源形態鍵。生成器按位置／法線誤差保留必要姿態，共用重複資料；骨架軌道、拓撲、UV、材質與原始動畫關鍵時間保留。最多同時使用兩個布料姿態，避免很多非零形態在 Compatibility 造成額外混合成本。

| 行走＋跳躍資產 | 修改前 | 修改後 |
| --- | ---: | ---: |
| 原始 GLB／遊戲副本 GLB 大小 | 108,214,784 B | 82,800,044 B |
| 全部部件 morph targets | 4,939 | 2,095 |
| Godot 匯入場景檔合計 | 47,658,091 B | 35,164,246 B |

逐樣本最大位置誤差 1.700 mm，法線向量差 0.04248。走路和跳躍衣服拓撲不同，落地恢復也需取樣兩套骨架，所以仍分階段預備兩套輕量副本；沒有宣稱合成單一模型或完全消除同步資源載入。坐姿使用既有小型 `graduate_rest.glb`。

已完成原生並排走路、跑步、起跳、翻轉、落地、坐姿檢視與 56 項匯入驗證。隔離角色測試的峰值 RSS 由 355,852,288 B 降至 267,509,760 B，但 P95 沒有同步改善；不將該結果冒充整個遊戲或 Web 記憶體。PCA 實驗雖再省記憶體，卻造成同時啟用的形態增多、P95 顯著惡化，故未採用。

原始來源 SHA-256、精度界限、全部隔離測試與實際畫面限制：[角色資產紀錄](avatar-memory-optimization.md)。

### 室內：簡易版先可用，進門才下載完整包

啟動僅包含室內簡易場景、共用簡易材質／256 px 圖片、配置與基本碰撞；不實例化所有室內。完整訓練室包標示 `startup:false`，排除啟動下載與「可漫遊」門檻；其他戶外背景下載保留。依賴檢查會阻止完整室內資源洩漏到啟動包。

上述網路拆包適用 Web。Windows 發行檔把完整遊戲素材保存在同目錄的本機 PCK，安裝／複製完成後不需每次 HTTP 下載；仍在進門後才準備詳細室內資源，不在啟動時實例化整間房間。

進門先建立簡易室內、出生點、出口和原有互動，之後才請求完整 Mesh／材質包。下載、驗證與掛載完成後，逐資源準備並在後續幀替換既有 MeshInstance 的視覺資源，保留節點、位置、比例、碰撞與互動識別。單次 `load` 仍可能超過預算，因此沒有將「分幀」等同於零停頓。

### 記憶體交接與包生命週期

背景下載改保存網路分段；Godot 寫入檔案並更新 SHA-256 後，回報消耗位置，JS 即釋放已交接段落。不再另外預先配置一份完整包大小的 JS 陣列。緩衝區的 `reserved_bytes` 是排程保留額度，`buffered_bytes` 才是當時仍持有的段落位元組；兩者分開記錄。啟動 gzip 解壓驗證後，使用 ReadableStream 把完整內容交給載入器，避免 `Response(BufferSource)` 在適配層再複製一整份解碼檔。

這些修改不表示整條下載路徑零複製：網路分段、JS→Godot 的 PackedByteArray、MEMFS、解碼模型及 GPU 資源仍各有生命週期。壓縮率也不等於 RAM 或 FPS 改善幅度。

Godot 沒有公開的逐 PCK 卸載 API；已掛載索引後續讀取仍可能開啟原包檔，故已掛載 MEMFS PCK 保留到分頁／程式結束。退出室內釋放場景、待套用 Mesh 與失去引用的視覺資源，但不刪除仍被索引的包檔，不宣稱 WebAssembly 記憶體會立即縮小。再次進入可重用掛載包；沒有新增跨重新整理的持久快取。

## 測試條件與指標定義

- 電腦：i7-1165G7，實體 RAM 8,269,398,016 B，Windows 11 Home。完整基準路線開始時可用實體 RAM 1,911,873,536 B，最低 347,070,464 B；最終路線開始 1,492,992,000 B，最低 317,988,864 B。背景程式沒有被自動關閉，兩次背景負載並非完全固定；每秒記錄可用 RAM，不以較早的單次系統快照代替整段測試環境。
- 瀏覽器：Chrome 154.0.8037.98；既有基準實際 WebGL GPU 為 **Intel Iris Xe／ANGLE D3D11**，不是因電腦有 MX330 就假設 Web 使用獨顯。
- 成對啟動測試：1200×800；路線測試：1280×800。每組前後各自沿用相同尺寸、瀏覽器、輸入路線與伺服器策略，不能將不同組數字互相套用。
- 原生單項資產測試實際使用 MX330／OpenGL；最終 Windows 程式尚未成功建立圖形裝置，因此沒有實際 GPU／FPS 比較。同機但不同 GPU 的結果本來也不能用來計算純粹 Web／原生引擎差距。
- 全部網路量測為 localhost，路線使用 `127.0.0.1:8951`；成對快取測試使用 `127.0.0.1:8952`。它隔離外網影響，可量本機下載／解壓／初始化，但不代表 GitHub、Cloudflare 或使用者家中網路速度。
- 啟動使用 Resource Timing、下載器階段與 engine ready 事件。`worldReady` 是世界初始化事件；`firstRafAfterReady` 是首次事件後幀回呼，不等同已驗證輸入。首次可操作以實際按鈕反應驗證；首次漫遊以角色與控制狀態驗證。
- Web 路線平均 FPS／P95 記錄有實際 WebGL clear 提交的 requestAnimationFrame 間隔，是 **CPU 提交節奏**，不是 GPU presentation 時間；同時保留引擎 FPS、draw calls、遮擋／串流計數。原生也分開標示採樣方法。
- 遙測 `process_ms`／`physics_ms` 來自 Godot `TIME_PROCESS`／`TIME_PHYSICS_PROCESS`，是前一個約一秒統計區間各自的最大耗時。`process_ms` 包含 SceneTree、RenderingServer sync／draw，**不是平均值，也不是 GDScript 專屬 CPU 時間**。依 [Godot 4.7.2 Main::iteration](https://github.com/godotengine/godot/blob/4.7.2-stable/main/main.cpp#L4679)解讀，不能用它直接斷言所有時間都花在腳本。腳本專屬 CPU 與 GPU frame time 尚未分別量測；上述小地圖原生 CPU 探針另計。
- 記憶體每秒讀取本測試啟動的瀏覽器完整程序樹。working set 加總可能重複計入共享頁面；private bytes 是程序私有提交量，不等於實際 RAM。JS heap、Godot allocator、WASM 與 GPU 專用／共用記憶體不混用。
- Web 回傳 0 的引擎記憶體監視器表示此平台不可取得，**不記成零占用**。實際 4 GB 裝置及獨立 GPU 記憶體峰值尚未量測，不能保證 4 GB 電腦都能達成固定 FPS。

## 同條件冷啟動與再次開啟

**冷開首次畫面並沒有改善**：這組最終值反而慢 0.517 秒，不因包較小就聲稱首畫面更快。最終冷開啟動包皆掛載較早，但 `contentReady` 只是 15 個啟動 PCK 已掛載；此時角色尚未準備完成，不能稱為首次漫遊。基準的同事件則等待 16 包，包含原本預載的完整室內；這是本輪指定行為改變的一部分。實際按鈕／漫遊驗證另列下方完整路線。

背景包的實際快取覆蓋也不同：基準再開 16 包中有 15 包命中磁碟快取，角色包仍傳輸 50,904,585 B（含 HTTP 標頭）；最終再開 15 包全命中，背景包網路傳輸為 0 B。因此基準再開不是「所有素材都已快取」，不能將再開差距全當成初始化改善。兩版伺服器規則與普通瀏覽器策略相同，沒有為某版強制預熱或擴大快取。

包下載與串流解壓互相重疊，**單獨總解壓 CPU 時間未量測**；不能把 `downloadingAt→verifyingAt` 全算成解壓。背景包在寫入時持續 SHA-256，`received→verified` 的 0～1 ms 只代表收尾，不是全包驗證成本。`verified→ready` 包含掛載與下一幀調度，總計基準冷／再開 1235／1100 ms、最終 457／458 ms，亦不能當作獨立 PCK 掛載 CPU 時間。兩份測試唯一 console error 都是根目錄 `favicon.ico` 404，沒有遊戲資源載入錯誤。

較早的 `low-end-baseline-startup.json`、`low-baseline-cache.json` 也保留；其中無痕 context 再開未命中二進位磁碟快取，不拿來充當本表快取結果。初始 `baseline.json`、`baseline-verified.json` 路線因 QA 捲動問題中斷，也不充當完整前後比較。

### 尚未解決的移動成本

另外完成同版 [移動診斷](../deliverables/low-end/low-final-movement_v2.json)，以真實按鍵沿無障礙道路移動，分別量一般、WebGL API 計時及 CDP 取樣三對靜止／移動階段。WebGL 計時那一對的串流 operations 全程維持 34，下載已完成；移動約 15.04 個世界單位，確實有持續行走。

慢點位於 Emscripten 畫面提交的狀態查詢，同時移動時多出大量動畫變形的 Transform Feedback 提交。這些是實測關聯，**支持動畫變形／渲染同步仍是後續優化方向**；API wall time 包含驅動同步等待，不能直接叫作純 GPU 執行時間，也不能靠刪掉等待來宣稱效能改善。未計時的診斷移動為 13.31 FPS，但那一段有 11 次串流操作，與上表的穩定串流條件分開解讀。
